# Verification map — lightbulb 0.2.2

This is the verify-gate record for 0.2.2 (main `73d8e59`). It maps each threat, each failure
mode and each parity row to the code that handles it and the test that proves it. Every
"Result" is from one `cargo test` run on 2026-10-24, on the tree of commit `9823842`
(see "Numbers" at the end). Real-Mac evidence is cited from `docs/acceptance-plan-a.md` and
`docs/acceptance-plan-b.md` by row; none of it was re-run here.

Notation: `src/x.rs:N` is the control. `tests/x.rs::name` is an integration test;
`src/x.rs::name` is a unit test in that file. **New** marks a test this pass added. For each
new test, the "made it fail" note says how the control was disabled in a scratch change to
see the test fail before the control was restored.

## Known gaps

Red rows: none. Untested or open:

1. **Sleep/wake on a real Mac** (B, C9) and **two real Macs on different networks**: not run on 0.2.2.
2. **C1**: the Grok → Claude hop has never passed on a real Mac (blocked by Grok's usage cap); the ring was not re-run on 0.2.2.
3. **C5**: held → Allow → next Cursor/Grok step is proven in two halves, not as one test.
4. **C8**: the bridge (Friday) is not in 0.2.2; only the engine's cloud-member side is tested.
5. **C10**: no fresh-Mac join on 0.2.2; the spec's "`leave` stops the service" is not what 0.2.2 does.
6. **Replay after 8 days.** `seen_ids` and finished outbox rows are pruned after 8 days (`src/outbox.rs:17`). An envelope its own sender resends after that is stored as new. Only that member's key can send on its connection, so no third party can do this; it is the same as the member sending again. No test.
7. **Hooks against a hostile local user.** The caller check stops an agent's own tools; any process of the same user can speak raw IPC to the socket (`src/hook.rs` header). There is no control for that, by design.
8. **Relay metadata.** A relay sees who talks to whom, when and how much. There is no padding or cover traffic. A team relay is set by an admin's roster entry, so a team trusts its admins with that choice.
9. **Presence clock skew under a day.** A peer up to 24 h ahead is accepted; if its clock then steps back, its later presences on the same connection are ignored until a reconnect (the first on each connection is always taken). Only that peer's own directory entry is affected. No test for the reconnect recovery path beyond `src/presence.rs::an_older_presence_is_ignored`.
10. **iroh's transport guarantees** are relied on, not tested here.
